# 本地续玩终局收据

当前实现用于内部经典30波、未计入Steam统计的战斗。玩家入口仍关闭；不能由本模块确认Steam服务器写入，也不计作完整30波或八关验收。

## 修复的问题

此前未计统计局的slot只有`{kind: uncredited}`，缺少跨进程的战斗身份。恢复后结算不会撤销磁盘上的旧战斗，菜单可以再次读入终局前进度。现在第一次保存先创建独立本地局记录，slot引用32位十六进制token及active收据的SHA256；再次保存与重启继续保留该身份。新开战斗使用独立token，不修改旧槽。

`run_local_lifecycle.gd`复用两快照存储的锁、闭合文件校验、恢复和原所有者重试。每局记录仅有active(1)和terminal(2)两个版本，没有统计计数或成就。目录是`user://continue/v1/local_runs/<token>/5088120/1`，数字1只是本地存储作用域，不冒用Steam账号。引用由当前安装的代码解释，不从存档加载任意脚本或路径。

## 提交与失败顺序

保存：真实世界HELD → 创建/核验active本地收据（计统计局继续使用原独立Steam收据）→ 写战斗槽。恢复：先检查本地收据，再准备私有世界；安装前再次检查。同一旧槽在terminal记录存在时返回`LOCAL_RUN_TERMINAL`，保留菜单和槽文件。

结束：Battle先进入END并关闭战斗操作，磁盘写入通过一次性的`process_frame`连接推迟到当前物理步结束后执行；不能用`call_deferred`假定已离开物理帧。ContinueFlow先确认terminal记录，随后才调用原结算/界面流程。若失败，场景保持暂停，结果不显示；提供四语重试结算及明确退出流程。重复胜负调用不能改写第一结果。只有明确由本对象提交或原所有者重试完成的terminal可作为本对象的幂等成功，另一个此前恢复的对象不能再次结算。原事务的锁释放失败只由保留该对象的所有者重试，另一个对象不能接管活进程锁。

本地slot提升为`classic_continue_slot_v2`，旧v1槽明确拒绝，不猜测给旧存档补身份或迁移。历史QA文件保留原版本语境。失去全部本地文件、手工回滚整个用户目录以及硬件断电持久性不属于已有证明；记录损坏时保留文件并拒绝继续。

## 保存与终局相撞

如果保存屏障刚进入REQUESTED而同一物理步终局，结束流程会断开尚未消费的保存回调，并在主循环调用`cancel_for_terminal`。它恢复原HUD/相机输入但不改变终局协调器的暂停状态；尚未写入的保存请求不覆盖旧槽。已持有真正冻结时钟的异常调用则拒绝取消并保留暂停，不能丢掉已有写事务。无本地收据的第一次保存遇同样时序时也走该取消流程，再显示普通结算，不平白创建已结束局的可继续槽。
