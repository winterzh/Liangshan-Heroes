## Unit 诊断能支持的结论

R2 为据守固定镜头的独立 10 秒诊断，timed 与 clockless 各覆盖 601 个物理步，初始部署和输入计划相同。16 个同步方法范围只在真实 `Unit._phys_body` 下统计。timed 的每步 exclusive 总和严格等于根 inclusive；观测到的呈现时间与同轮 M1 原始帧间隔逐项匹配。

| 范围 | inclusive ms / 物理步 | exclusive ms / 物理步 |
| --- | ---: | ---: |
| `unit._phys_body` | 3.702 | 1.612 |
| `unit._do_chase` | 1.313 | 0.297 |
| `unit._follow_path` | 1.136 | 0.479 |
| `unit._acquire` | 0.237 | 0.050 |
| `unit._begin_amove` | 0.226 | 0.216 |
| `unit.current_move_speed` | 0.290 | 0.157 |
| `battle.can_unit_step` | 0.193 | 0.193 |

根 exclusive 约占根 inclusive 的 43.6%，它是尚未细分的工作与观测开销，不是已证明可以去掉的成本。下一步先细分这里的健康态检查、状态/技能计时、动画/尘粒处理；再根据结果选择一项保持原规则的候选。路径跟随是已命名范围中较大的剩余成本，但尚未证明哪一个表达式或数据结构值得改。

inclusive 子范围互相嵌套，不能把表内 inclusive 相加。两种诊断均有包装器开销，不能从 clockless 帧率相减得出真实生产成本或优化收益。clockless 原报告的 `nested_time_conservation=true` 是不适用的标签：该模式实际只保留调用次数，时间为 -1，没有执行时间守恒。当前分析器已改为 null，并用原始结果离线核验；原收据不重写。只有 timed 做了时间守恒。

独立复核发现并修复了工具生命周期问题：完成码现在在 finally 收尾后决定；锁后的初始化也进入 try/finally；诊断复制按完整基线 SHA/Git blob 白名单绑定，5 个派生文件的 before/after 与观察器/scope JSON 全部核对。完整基线实际运行的旧 wrapper 被按其收据 SHA 保留，真实收尾守卫均通过。工具修复本身不计为游戏性能提升。

## 后续候选与终验边界

1. 先测根 exclusive 余量的明确子项，然后只在私有派生工程试一项；不得改变 60 Hz、游戏速度、寻敌/攻击规则、RNG 调用语义或以减兵减特效换帧率。
2. 仅当功能/状态/RNG 回归通过，并在同机、同冻结输入、标准特效的正常完整窗口中重复改善压力段且没有明显尾延迟/内存回退，才考虑采用。短插桩结果只用于定位，不能晋级生产。
3. 追击 fallback、分离建桶 fastpath、未证明的预加载保持停止状态。没有新反证时不重复这些已排除路线。
4. 生产接入时 Battle/Unit 由单一任务独占；性能候选与稳定身份/续玩候选分别保留基线、补丁和收据。先验收并冻结一个接入点，再重新建立另一条路线的对照，不能把混合源码跑出的 PASS 分摊给两项改动。

最终仍需同机 M1 全矩阵与压力段审查、源与成品 PCK、标准 30 波、八关成功流程和真人体验；长时间 soak 与设备兼容性另行完成。本轮没有填补这些尚未运行的门槛，也没有实现玩家继续本局入口。

## 可复现入口

本机引擎路径继续从被忽略的 `godot.local.txt` 获取，公共命令不写死个人路径。首次运行前应按当前受测提交重新冻结，旧 private run 不复用结果。

```text
py -3 -B tools/run_stabilization_performance.py --source-head <当前受测提交> --run
py -3 -B tools/prepare_unit_remainder_diagnostic.py --baseline-run <新完成的完整M1目录> --output <全新诊断目录>
py -3 -B tools/run_unit_remainder_diagnostic.py --prepared <该全新诊断目录> --run
```

本轮仅修改性能/隔离验收工具和专属 QA/说明；公共交接文档、逐文件 Git 提交和推送由主任务统一收尾。源码同步不等于 Steam 更新。
