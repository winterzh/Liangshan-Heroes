## 唯一候选：单一移动类型的局部建桶快路，先测准备成本

这是**待证伪实验**，不建议立即改生产。当前只能证明完整分离有约 2.150 ms/步的前段预算，不能证明其中字符串分组/字典构建值得改。Unit 的 3.929 ms/步更大，但原生单标签也不足以支持再做某个 Unit 微调。

**先用最小诊断决定是否值得做：** 保持当前完整算法，一次 solve 只在大阶段边界计时：① sources/快照/导航初读；② `profile_cells` 构造；③ 原有逐对求解；④ 最终写回。计时进程每调用只读少量时钟，不按候选对打时间戳；另一个计数进程记录分派路径、有效 profile 个数、源数/桶数、候选对/实际重叠对、完整导航回退数。保持现有 M1 300 步热身与测量 tick 锚，报告前 600 步；这些子段不能再加到 separation 总项。

如果 ② 的成本很小或混合 profile 占比高，直接否定本候选；不因函数内存在字典就继续优化。作为工作量筛选，可要求这段在目标前 600 步中的潜在可省预算至少约 0.5 ms/步，再准备候选；这不是收益保证或验收线。仅有几十/一两百微秒潜力时，应返回 Unit 粗分段，不能宣称这是解决 30 FPS 的主路线。

**若证据成立，最小实现只改同步建桶：** 在已经读取 profiles 的原快照循环内同时判定 sources 是否具有同一个精确 profile 字符串；无需新增一遍 Node 扫描。只有本次已证明单一 profile 时，为每个原桶直接构造 `[max_id, PackedInt32Array(active_indices)]` 的一个局部 cells 字典，省去每桶临时 groups 与外层 `profile_cells[profile]` 构造/查询。混合 profile 原样回到现有通用路径。不能把“不是 water”合并成 land；未知 profile 字符串仍按原精确分组语义处理。即使 source 只在旧桶中、已经退出 units，也必须参与该证明；宁可保守退回通用路径。

这与历史“相邻九桶列表复用”不同：仍在原双循环里逐桶查询，绝不预拼九格邻居列表；也不排序、二分或切片。它只是在已证明单一类型时省去通用分组结构，保留已经采用的 ACTIVE 筛选及最大 ID 整桶拒绝。其单桶结构与早期 bucket-max 尝试相近，但旧尝试没有这项局部单类型证明和通用回退，旧计时不能作为新快路收益。

**不可变约束与必要验证：** Battle 分派门槛、`_sep_phase`、sources/indexes/order 去重及重复 order、原桶迭代和条目顺序、bucket-only 邻居、旧网格中的死亡/驻军邻居语义、active 剧情筛选、金矿相位、浮点运算顺序/精度、原 NAV_OPEN 与跨格回退、最终写回均不改。用同一批真实 Unit/地图，冻结完整现行 solver/dispatch，与候选逐次恢复相同输入，比较完整向量值、状态和桶顺序；复用 crowd_nav 的密度/人数门槛、混合陆水、未知 profile、重复/乱序/空桶、桶外主列表、建桶后位移、撤退和直接改导航、格线/非有限半径夹具。新加“连续两次调用间由单一切混合再切回”、全部 profile 相同但为未知字符串、不同 profile 只出现在 bucket-only/非 ACTIVE source 的夹具，保证快路仅影响性能。

完整计时要把证明、建桶、求解、写回全部计入，不只计内部碰撞循环；采用双方预热、同批输入、交换先后顺序的配对窗口，先检查 64/128/206/320 的单 profile 密集、混合 profile 与稀疏回退。任何位置/顺序差异即撤回；完整函数收益不稳定或回退路径显著变慢也撤回。只有行为和完整函数证据成立，才进入当前完整源码的无插桩 M1 60 秒×3、固定/自动镜头统计。当前 V2 会改变绘制及战斗墙钟演化，届时应重新冻结完整源码，不能沿用本次 4baafc1 原始帧作对照。
