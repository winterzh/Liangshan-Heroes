Three independent phases use the same driver/source set and separate actual
processes/private profiles. Choose one explicitly; default is `freed_pending`:

- `freed_pending`: real item allocation and `_begin_item_cast`, actual Unit timer
  advancing to 0.375 remaining, real target.free, capture/JSON/validate, real fresh
  Battle and Unit/inventory fixture state, shared live tombstone bind/release, then
  original `_tick_pending_item_casts`. A positive timer is checked before the real
  remaining timer expires. Exact original and restored consumer calls each have a
  persisted checkpoint. Expected desired behavior is cancellation without cost;
  the current known risk may fail this phase. Keep the failure.
- `freed_walk`: same process through original `_queue_walk_item` with the actual
  unit-target INF sentinel. After free and restore, call the actual walking pass.
  Do not inject a finite point merely to force a different branch. Cancellation,
  no spend/cooldown/FX and no repeated action are checked on both sides.
- `lifecycle`: retains the old unexecuted broad fixture: two ordered queues,
  actual allocation above 2^53, swap/UID lookup, shared cooldown, consumed/missing
  UID, expired target/caster, cancellation/new order, timeout, 12 real timer/pass
  pairs, explicit staged arrival and once-only healing/consume. Expired pending
  remains present, so current production can fail before completing this phase.
  This is not silently reduced to a green-only case set.
