# Stable Unit identity and Battle simulation clock — bounded proposal

Prepared against the exact files in `source_pins.json`. Production, public QA, shared documents and Git were not changed; no Godot process was run. `callsite_inventory.json` contains **63 native-ID/frame API source lines** and **71 modulo source lines**. These are source occurrences, not runtime frequencies or test counts. The first informal message estimated 67; the recorded enumeration is authoritative.

The minimum production change is one persistent positive `Unit.entity_id`, one Battle-owned allocator, one Battle-owned simulation tick and explicit outer commit state. This establishes new-build uninterrupted/restored equivalence; it cannot preserve every ordering or modulo value previously produced by process-global ObjectDB allocation. Never reconstruct IDs from new ObjectIDs, an array index, padding allocations, or saved native remainders. All accepted saves must carry the new trusted content identity and schema.

## Identity allocation and construction

Use positive signed int64 IDs, with `9223372036854775807` reserved as the exhausted **next counter**, never issued. Initial next ID is 1. Allocate from one Battle domain for every actual Unit node: heroes, ordinary troops, workers, buildings, resources, summons, dying Units and any captive Unit belonging to that Battle. A `Unit.new()` used only as the Android capability probe is not an entity and remains ID 0; an ID-0 Unit may never enter `units_root`, `units`, sorting, crowd solve or a save registry.

Reserve before constructing/publishing a runtime Unit and assign its ID before `add_child`/`setup` can expose it. Reservations are monotonic and **burn on later failure**; gaps are valid and counter rollback is forbidden. Batch reservation is available for an authored multi-summon operation so it can reject insufficient capacity before any member or cost is committed. Do not number only successfully visible/mobile units: buildings/resources/queued dying nodes are part of the complete graph. Existing `_ai_spawn_serial` remains a separate successful-mobile-spawn counter; its `AI_TICK_PHASES` schedule must not be recomputed from entity IDs.

`spawn_unit`:717 currently publishes a fresh Unit before checking terrain and restoring retired inventory. Terrain failure and inventory rejection queue that node for deletion. A reserved ID must not be reused; restore/capture cannot proceed until that queued shell is gone. Keep `hero_item_progress` unchanged on failure, as the tested item-UID change already does. The allocator must not touch the independent item-UID counter or regenerate item UIDs.

Death removes a Unit from the activity array but its falling body can remain in `units_root`; it retains the same entity ID and stays in the full graph until actually freed. Resource depletion and summon TTL death never decrement the allocator. Hero resurrection constructs a **new entity ID**, while hero key-based combat/progress accounting and existing inventory stack UIDs retain their present behavior. A genuinely restored Unit takes the saved ID without invoking `spawn_unit`, `setup`, RNG or allocation. A restored allocator begins above every validated known persistent entity ID; it must restore the saved counter, not replace it with `max(live)+1` and thereby forget previously issued/dead IDs.

`clear_campaign_section`:17109 resets the existing mobile-AI counter and phase intentionally. It must **not** reset the new Battle entity allocator or monotonic simulation tick. A genuinely new Battle gets a fresh domain. This preserves ordinary campaign lifecycle while save eligibility remains standard-defense-only.

## Simulation clock and capture barrier

The new simulation tick labels each eligible unpaused world physics step. It starts at zero; at the beginning of a step it advances once and remains **open** until the outer barrier confirms all callbacks and deferred deletion work have completed. Capture rejects an open or faulted step. Overflow rejects before incrementing. A pause/menu wait must not advance it, and several catch-up physics steps within one rendered frame each advance it once.

Do not simply rename `_ai_tick_frame`. Current Battle returns during INTRO before incrementing that field, while Unit has no equivalent phase check. `_ai_tick_frame`, `_ai_spawn_serial`, `ai_tick_phase` and `_sep_phase` retain their existing schedules and become explicit Battle/Unit state. `_sep_phase` cannot be derived from the new tick: its method skips different phases and can be called independently by QA. Do not replace delta-based cooldown, fog, wave or effect clocks with integer ticks in this narrow migration.

RunSession should own one early `SceneTree.physics_frame` hook for the active world: finish the preceding open step, then begin the next only when the world is allowed to simulate. This labels all Battle/Unit/effect callbacks without changing their order or priority. The normal `process_frame` boundary can commit the final physics step of a rendered frame. A capture request is latched and serviced at a boundary; it must stop command/input admission and pause the world **before** starting another step, then allow already queued work/deletions to settle while paused. Validate that no retained graph node is queued for deletion. A callback fault invalidates the step instead of publishing it as committed.

The native 4.6.3 ordering is: physics signal, node callbacks, deferred messages, physics timers/tweens, deletion queue; the next process signal precedes process callbacks. Thus Battle's method tail and its own `call_deferred` are both too early to certify the entire previous step. This recommendation is based on [SceneTree implementation](https://github.com/godotengine/godot/blob/4.6.3-stable/scene/main/scene_tree.cpp#L586); the actual integrated hook order, commands and paused deferred work still need a real engine test. The value core cannot prove an external caller obeyed this barrier.

For the two gameplay caches, use the current local tick and integer division (no float conversion). `_eco_lane_cache` persists for up to 16 steps and contains hero references, lane assignments and pressure; it is **not** safely discarded and recomputed at an arbitrary restore point. Persist its bucket and full ordered value/reference structure, or restrict a documented save boundary to an actual normal invalidation point and test it. `_res_block_cache`, `_focus_counts` and spatial grids can only be classified as derived if no input, Unit or effect can consume them before the same normal rebuild that the uninterrupted run would perform. Their rebuild must preserve `Battle.units` order. “Clear all caches on restore” is not a sufficient continuation argument.

## Unit and graph schema changes

Add one top-level declaration `var entity_id: int = 0`: the current 272 Unit declarations become 273. It is authoritative gameplay data, not visual omission or metadata. Choose `defense_unit_state_v2` and `defense_unit_graph_v2`; previous v1 snapshots lack proof of a persistent allocator and cannot silently qualify as whole-run resumes.

The Unit factory must explicitly read/assign `entity_id` (native positive int64), enforce its equality with the canonical decimal `record.entity_id`, and reject ID 0, MAX sentinel, duplicate graph IDs, malformed decimal or counter violations before allocation. The record envelope remains the graph identity; adding the value field creates a checked redundancy, not two independent identities. Every instantiate sets the saved field while detached/disabled before references bind. Extend the explicit RULES/read/assign inventory and declaration coverage by one; do not conceal the new declaration under ignored fields. No integer travels through JSON float: use the existing exact value codec and canonical envelope text.

Graph capture builds `object_to_id[unit] = str(unit.entity_id)` from the complete ordered root. It must verify uniqueness, valid range and allocator bound, then call the unchanged shared GraphIdentity registry logic. Graph prepare validates **every** record and allocator first, instantiates/binds off-tree, keeps the identity open for all other effects, and returns one unactivated candidate. Only the outer transaction attaches/activates the whole graph and commits all Battle counters together. Old Battle remains untouched on any failed final record. IDs must not be reassigned by attachment order.

Keep separate schemas/counters for item stack IDs, native retired/source tokens, ability/wall/ward serials and the new entity allocator. All must be captured by the eventual root transaction; this candidate covers only the entity/tick core. Native hit/source/equality domains continue to use the tested shared mapping and are not silently converted to a different scalar domain.

## Executable preparation and next actual proof

`entity_clock_core.gd` is a small dependency-injected value candidate. A Battle would own exactly one instance; its accessors are the authority for the proposed `next_entity_id` and `simulation_tick`. It exposes `reserve`, `can_reserve`, `begin_step`, `commit_after_callback_barrier`, `invalidate`, `capture`, `validate`, and `restore_fresh`. It imports no Node, Engine, global RNG or source path. `known_entity_ids` is the complete distinct live Unit registry, including dying nodes, with the existing 4096-node graph budget; the saved monotonic counter also retains burned/dead allocations. Other retained graph references still require the existing complete schema validation. The module itself neither discovers that registry nor proves the outer barrier.

`core_smoke.gd::run(core_script, codec_script)` returns 18 labeled checks and can run under an existing root-controlled driver. It uses actual JSON stringify/parse and exact codec values, includes 2^53+1 and int64 limits, burned reservations, next allocation/tick continuity, rejected open captures/rewinds/bad IDs/content/unknown fields, and faulted-step refusal. It is **not run** and is not a real Battle restoration test. Its literal `fixture-core-v1` is only a unit-level test fixture; production always supplies the actual runtime provider identity.

The next actual integrated smoke must use a real source-identified Battle/Map/Units and the v2 factory: successful/failed spawns, nonmobile entities, dying root nodes, summon expiry, hero respawn, >1000 allocations, shuffled persistent IDs versus root order, equal-queue ties, both direct and buffered crowd paths plus >320 phased separation. Save at a nonzero/non-16-boundary clock, restore in another process with different native IDs/engine-frame origin, continue the same command/RNG sequence and compare stable-ID decisions, positions and phase traces. Include a pause with several global frames, catch-up with multiple local steps, the last physics step before capture, queued deletion and a failed last graph record. Compare the candidate with itself before/after restore; existing v1/native-ID historical results remain separate.

This preparation does not implement whole Battle restore, all effect clocks, command queue admission, RunSession, disk storage, PCK entry or resume UI. No performance improvement or unchanged legacy native-ID trace is claimed.
